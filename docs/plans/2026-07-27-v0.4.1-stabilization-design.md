# v0.4.1 Stabilization Design

## Goal

Produce a `v0.4.1` stabilization candidate that preserves every existing
Windows release gate, fixes the failures demonstrated by the `v0.4.0` main
workflow, closes the known Windows journal and SID robustness gaps, and leaves
only live disposable-Windows certification for later execution.

## Constraints

- Preserve the published `v0.4.0` tag.
- Keep the restricted and elevated disposable-Windows jobs in the main CI
  workflow. Missing workers must remain visible as queued certification work.
- Do not weaken sandbox guarantees or change report semantics merely to satisfy
  stale tests.
- Use regression tests before production changes.
- Keep the patch release focused: no unrelated package-layout or backend
  redesign.

## Failure Evidence

The `v0.4.0` main workflow at commit `15e604e` demonstrated these failures:

1. `govulncheck` ran under Go 1.26.4 and reported GO-2026-5856 in `crypto/tls`;
   the standard-library fix is Go 1.26.5.
2. Both Linux jobs failed the facade test because it constructed an executor
   without satisfying the Linux `sandbox.Init()` contract.
3. The Linux rung-2 job exposed writable-root, `/tmp`, grant, mount-view, and
   compile-report expectation failures.
4. Local `make lint` exposed bounded integer conversions and caller-controlled
   path operations. Most conversions are deliberate binary encoding, but the
   restricted journal should use root-anchored access and bounded reads, and SID
   derivation should reject identities too large for its persisted length field.
5. The live Windows restricted job remains queued; the elevated job correctly
   depends on it.

## Architecture

### CI and toolchain

Set the workflow Go version to 1.26.5 and run the module-pinned vulnerability
scanner rather than installing `@latest`. This makes local and CI release gates
reproducible while consuming the standard-library security fix.

### Linux stabilization

Treat the Linux failures as three separate contracts:

- public facade initialization;
- policy/report representation;
- kernel-enforcement input construction.

Tests will first reproduce the CI behavior under Linux. Fixes will preserve the
documented `Init()` requirement, canonical report status vocabulary, and
fail-closed filesystem/network behavior. Where tests are stale after the package
layout change, update the tests to the public contract; where runtime policy is
wrong, change production code and retain the failing test as a regression.

### Windows journal hardening

Open and retain an `os.Root` for the journal state, and perform record access
relative to that root. Journal enumeration will accept only regular,
non-reparse records with valid names. Reads will be capped before JSON decoding.
Durable record creation and removal will use root-relative operations so
ambient path replacement cannot redirect cleanup state outside the journal.

### SID and binary-encoding robustness

Keep the persisted SID derivation ABI unchanged. Validate installation and
executor identity lengths before converting them to the existing 32-bit length
prefix. For other gosec findings, add explicit bounds where a caller can
influence size; use narrowly documented `#nosec` annotations only where the
conversion is an intentional, already-bounded instruction or wire encoding.

## Verification

The candidate must pass:

- focused red/green regression tests for every corrected behavior;
- `go test -race -count=1 ./...` on the local host;
- Linux CI-equivalent rung-1 and rung-2 suites;
- `make test-windows-build` for amd64 and arm64;
- `make lint`;
- `make vuln`;
- formatting, diff, and workflow syntax checks.

Independent specification and code/security reviews occur after the Linux/CI
phase and again after the Windows-hardening phase. Live Windows certification
remains pending until the retained self-hosted jobs execute on matching
disposable workers.
